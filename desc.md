# Задание проекта
Проектная работа: контейнеры и CI/CD для Kittygram
Проходной балл проекта «CI/CD для Kittygram» — 9 баллов. После его получения проект нельзя будет сдать на дополнительную итерацию ревью.
Для этого проекта вам понадобится репозиторий kittygram-final. Клонируйте его на локальный компьютер и выполняйте задание в нём.

И что же надо сделать?
В этом проекте вам предстоит:
создать проект Kittygram у себя в GitHub;
внести изменения в код бэкенда, чтобы он смог работать с СУБД PostgreSQL;
настроить проксирование в Nginx к бэкенду;
описать сборку бэкенда Kittygram в Dockerfile;
настроить запуск проекта Kittygram в контейнерах с помощью Docker Compose;
настроить автоматическое тестирование;
выполнить деплой этого проекта на удалённый сервер.
Автоматизацию надо настроить с помощью сервиса GitHub Actions.
При пуше в ветку main:
проект должен тестироваться;
в случае успешного прохождения тестов образы должны обновляться на Docker Hub;
на сервере должны быть запущены контейнеры из обновлённых образов;
после запуска контейнеров должны быть выполнены автотесты.
Вы уже создавали виртуальную машину через сервис «Учебные окружения» в уроке «Получение доступа к серверу», когда изучали скриптовые языки и управление ОС. Деплой проекта Kittygram выполняйте сюда же. Создайте или запустите её заново по той же ссылке:
https://infra.education-services.ru/activate/cse-linux
Сервисы будут запущены в виде Docker-контейнеров. Вы уже в общих чертах знакомы с этой технологией. На данном этапе достаточно изучить основные директивы, которые понадобятся в данном задании. 
Работать будет удобнее, если под рукой есть шпаргалка с перечнем команд и инструкций для Docker, workflow и GitHub Actions.
Подсматривать можно и нужно, пользуйтесь!
Какие образы и контейнеры вам понадобятся:
Имя образа	Название контейнера в docker-compose.yml
kittygram_gateway	gateway
kittygram_backend	backend
kittygram_frontend	frontend
postgres:13	postgres
Должны быть подключены Docker volumes:
static — для хранения файлов статики контейнеров backend и frontend. Доступ к этому volume должен быть и у контейнера gateway, чтобы Nginx мог раздавать эти файлы.
media — для хранения файлов, загружаемых пользователями. Доступ к этому volume должен быть и у контейнера backend, и у контейнера gateway, чтобы Nginx мог раздавать эти файлы.
pg_data — для хранения данных PostgreSQL из контейнера postgres.
Архитектура приложения в контейнерах:

Шаг первый: настройка контейнеризации
Напишите Dockerfile для образа kittygram_backend. За основу можно взять Dockerfile для бэкенда Taski.
Для создания образа kittygram_gateway используйте готовый Dockerfile из папки nginx/.
Обновите конфигурацию Nginx и добавьте проксирование запросов для API и админки. Также нужно добавить путь к месту для хранения файлов, загруженных пользователями (volume media).
Для создания контейнера фронтенда используйте готовый Dockerfile из папки frontend/.
Настройте совместную работу контейнеров backend и postgres:
настройте Django для работы с PostgreSQL;
создайте файл .env для PostgreSQL и контейнера backend: впишите в него переменные для инициализации БД и связи с ней.
Допишите docker-compose.yml, заготовленный в репозитории. В нём уже есть описание контейнеров, но его нужно расширить:
добавьте volume для статических файлов админки и фронтенда;
добавьте volume для хранения файлов, загруженных пользователями;
подключите файл .env к контейнерам postgres и backend.
Шаг второй: подготовка удалённого сервера
Подготовьте свой удалённый сервер к публикации проекта Kittygram:
Установите Docker по инструкции из официальной документации или командами из шпаргалки.
Создайте директорию kittygram/ в домашней директории сервера.
Убедитесь, что порт, который будет использоваться для доступа к kittygram_gateway из сети интернет, не занят какими-либо другими приложениями (например, командой netstat -tulpn | grep <port>).
После подготовки разверните Kittygram на сервере автоматически с помощью GitHub Actions.
Шаг третий: настройка CI/CD
Автоматизируйте тестирование и деплой проекта Kittygram с помощью GitHub Actions.
Напишите в файле .github/workflows/main.yml workflow, который будет:
Проверять код бэкенда в репозитории на соответствие PEP8.
Запускать тесты для фронтенда и бэкенда (автотесты уже написаны и лежат в директории tests/).
Собирать образы проекта и отправлять их на Docker Hub (замените username на ваш логин на Docker Hub):
username/kittygram_backend;
username/kittygram_frontend;
username/kittygram_gateway.
Обновлять образы на сервере и перезапускать приложение при помощи Docker Compose.
Выполнять команды для сборки статики в приложении бэкенда, переносить статику в volume, выполнять миграции.
Извещать вас в Telegram об успешном завершении деплоя.
❗️ Не указывайте чувствительные переменные, такие как SSH-пользователь и SSH-ключ для деплоя, в открытом виде. Используйте для этого GitHub Secrets. Пример — key: ${{ secrets.SSH_KEY }}. 
Также не храните в репозитории файл с переменными окружения .env. Либо положите его вручную на сервер, либо храните его содержимое в GitHub Secrets и во время CI/CD добавляйте на удалённый сервер.
Чтобы задание можно было проверить автоматическими тестами, создайте в корне проекта файл tests.yml и заполните его следующим образом:

repo_owner: ваш_логин_на_гитхабе
kittygram_domain: полная ссылка (http://<ip-адрес вашей ВМ>:<порт gateway>) на ваш проект Kittygram
dockerhub_username: ваш_логин_на_докерхабе  
Пример заполненного файла:

repo_owner: stasbasov
kittygram_domain: http://51.250.97.10:9000
dockerhub_username: stasbasov
