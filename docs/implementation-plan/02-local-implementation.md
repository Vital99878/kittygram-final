# Этап 2. Локальная реализация

[Общий план](README.md) · [Назад: архитектура](01-architecture.md) · [Далее: сервер и CI/CD](03-cicd-deployment.md)

**Входное условие:** можем объяснить архитектуру из этапа 1. **Результат:** Kittygram работает через один адрес gateway на локальном компьютере, а данные сохраняются при замене контейнеров.

Каждый блок завершаем проверкой и небольшим коммитом. Приведённые команды — ориентиры для будущей практики; состав файлов и настройки сначала готовим в соответствующем блоке.

## 2.1. Проверить окружение и подготовить репозиторий

**Разбираем:** какие инструменты работают на Windows, какие внутри Linux-контейнеров, где находится корень репозитория и откуда Docker получает контекст сборки.

**Делаем:**

- Проверяем рабочую копию и ветку, Docker Desktop в режиме Linux-контейнеров, доступность Docker Engine и Compose. Для этого пригодятся `git status`, `docker version`, `docker compose version`.
- Выбираем терминал для локальных действий. PowerShell, Git Bash и shell внутри контейнера обозначаем явно; синтаксис переменных не переносим между ними молча.
- Проверяем версии из Dockerfile и requirements на совместимость. Версии инструментов фиксируем осознанно, отдельно учитывая ограничения учебного шаблона.
- Готовим `.gitignore`, контексты сборки и `.dockerignore`, чтобы `.env`, локальные зависимости и служебные файлы не попадали в образы.
- Приводим пример `_env.example` к предусмотренному заданием `.env.example`. Создаём локальный `.env` с учебными значениями; в Git оставляем только пример.

**Результат:** рабочее окружение проверено, определены версии и места выполнения команд.

**Готово, когда:** Docker CLI видит Engine, Compose доступен, а `git status` показывает только ожидаемые изменения. Образ не требует заранее установленного на Windows Python или локального `node_modules`.

## 2.2. Подготовить Django к PostgreSQL и контейнерному запуску

**Файлы:** `backend/kittygram_backend/settings.py`, `backend/requirements.txt`, `.env.example`.

**Разбираем:** Django читает настройки и через драйвер подключается к базе; PostgreSQL является отдельным сервисом. Gunicorn запускает приложение, а Nginx направляет к нему запросы.

**Делаем:**

- Заменяем SQLite-настройку на PostgreSQL с параметрами из окружения: имя БД, пользователь, пароль, хост, порт. Для Compose хостом будет имя сервиса `postgres`.
- Согласуем переменные инициализации PostgreSQL с переменными подключения Django. Проверяем уже существующий `psycopg2-binary`, добавляем совместимый Gunicorn в зависимости запуска.
- Выносим `SECRET_KEY`, режим отладки и разрешённые хосты в конфигурацию. Строку `False` разбираем как логическое значение, а не через обычное `bool()` от непустой строки.
- Убираем неоднозначность двойного объявления `STATIC_ROOT`; согласуем `STATIC_ROOT`, `STATIC_URL`, `MEDIA_ROOT`, `MEDIA_URL` с архитектурой хранения.
- Разбираем миграции: они меняют схему выбранной БД. Переход на PostgreSQL сам по себе не переносит прежние данные из SQLite; если нужны старые записи, перенос обсуждаем отдельно.

**Результат:** бэкенд получает настройки извне и готов подключаться к PostgreSQL.

**Готово, когда:** после подключения базы в блоке 2.4 проверка Django и миграции проходят именно с PostgreSQL. Можем показать, какое значение используется как адрес БД и откуда оно пришло, не раскрывая пароль.

## 2.3. Собрать образы и понять их содержимое

**Файлы:** новый `backend/Dockerfile`, выданные `frontend/Dockerfile`, `nginx/Dockerfile`, необходимые `.dockerignore`.

**Разбираем:** базовый образ, рабочий каталог, контекст сборки, установка зависимостей, кэш и команда запуска. Для каждой инструкции выясняем, выполняется ли она при сборке или при старте контейнера.

**Делаем:**

- Описываем образ бэкенда: совместимый Python, зависимости, код и запуск Django через Gunicorn на согласованном внутреннем порту.
- Читаем существующий Dockerfile фронтенда: почему нужен lock-файл для `npm ci`, где появляется `/app/build`, что делает заданный `CMD`.
- Проверяем образ gateway и способ загрузки Nginx-конфигурации.
- Собираем три образа локально. По логу сборки определяем выполненные и закэшированные шаги.
- Проверяем, что нужные файлы и команды есть в образах. Подключение к БД проверяем уже в составе Compose, когда есть база и окружение.

**Результат:** три локальных образа с понятным назначением.

**Готово, когда:** сборка воспроизводится из репозитория и зависимостей, а на этапе `docker build` не требуется работающая production-БД. Миграции не прячем в сборку образа.

## 2.4. Описать сервисы, сеть и тома в Compose

**Файл:** новый `docker-compose.yml`.

**Разбираем:** `services`, `build`, `image`, `ports`, `volumes`, `env_file`, `environment`, `command`, `depends_on`, `healthcheck`. Смысл каждого ключа связываем с этапом 1.

**Делаем:**

- Описываем `gateway`, `backend`, `frontend`, `postgres` и тома `static`, `media`, `pg_data`.
- Согласуем сеть, имена сервисов, внутренние порты и один опубликованный порт gateway.
- Передаём настройки только нужным сервисам. Параметры инициализации БД проверяем при первом создании её хранилища.
- Задаём пути монтирования. Nginx предоставляем чтение файлов; запись frontend и backend направляем в предусмотренные каталоги.
- Определяем одноразовую команду frontend для переноса сборки. Не монтируем том так, чтобы скрыть исходную `/app/build` перед копированием.
- Добавляем проверку готовности PostgreSQL. Различаем `depends_on` с условием готовности и простой порядок старта; завершение одноразовой операции также проверяем отдельно.

**Проверки:** `docker compose config --quiet` проверяет конфигурацию без вывода значений, `docker compose ps -a` показывает в том числе завершившийся frontend, `docker compose logs` помогает выяснить причину ошибки.

**Готово, когда:** база готова, Django подключается к ней по имени сервиса, frontend успешно переносит файлы, gateway запускается. Полноценные HTTP-сценарии проверяем в следующем блоке.

## 2.5. Связать Nginx, статику и фотографии

**Файлы:** `nginx/nginx.conf`, пути и команды в Compose, при необходимости настройки static в Django.

**Делаем:**

- Направляем `/api/` и `/admin/` к backend; разбираем сохранение пути запроса в `proxy_pass` и нужные HTTP-заголовки.
- Настраиваем выдачу React и возврат `index.html` для клиентских маршрутов. API и отсутствующие файлы не должны случайно превращаться в успешный HTML-ответ.
- Выполняем миграции, `collectstatic` и перенос файлов в том. Выбираем согласованные каталоги и URL: React и Django сейчас используют `/static/`, поэтому требуется явное разделение маршрутов либо отдельный `STATIC_URL` Django.
- Проверяем, что повторная публикация frontend обновляет его файлы и не стирает Django static или media. Не очищаем общий том целиком ради замены одной сборки.
- Настраиваем `/media/`: backend записывает фотографию, Nginx читает тот же файл через своё монтирование.

**Проверки в браузере и Network:** главная страница, JS/CSS, клиентский маршрут после обновления страницы, API, админка со стилями, загрузка и просмотр фотографии. Для JS проверяем содержимое и тип ответа, а не только статус `200`.

**Готово, когда:** все сценарии работают через адрес gateway. Можно показать соответствие URL фотографии файлу в `media` и объяснить, почему база хранит сведения о файле, а не заменяет файловое хранилище.

## 2.6. Проверить приложение и освоить диагностику

**Разбираем:** линтер, тест поведения, проверка конфигурации, проверка готовности и внешний приёмочный тест отвечают на разные вопросы.

**Делаем:**

- Запускаем проверку PEP8 для кода бэкенда; определяем явные зависимости инструментов проверки.
- Запускаем имеющийся React-тест в однократном режиме, подходящем для CI.
- Определяем и добавляем небольшой набор backend-тестов: например, отказ при некорректной регистрации, ограничения доступа и создание/получение котика. Для операций с БД используем отдельную тестовую базу.
- Проверяем число найденных тестов. Системная проверка Django полезна, но не заменяет проверку поведения API.
- Практикуем короткую диагностику: остановлен backend → смотрим статус и логи; ошибочный DB host → проверяем окружение и сеть; пропало изображение → проверяем media и маршрут Nginx.

**Результат:** известны команды локальных проверок, их зависимости и ожидаемые результаты.

**Готово, когда:** можем отличить ошибку приложения от ошибки маршрутизации, зависимости или конфигурации и выбрать первый источник информации. Весь корневой `pytest` пока не используем как обязательное условие: часть его тестов требует Docker Hub и сервера.

## 2.7. Проверить сохранность и повторяемость

**Делаем контрольный проход:**

1. Регистрируем учебного пользователя, создаём котика и загружаем фотографию.
2. Пересоздаём контейнеры, сохраняя именованные тома. Не добавляем `-v` к удалению окружения: этот флаг меняет условия проверки и может удалить данные томов.
3. Проверяем вход, запись о котике и доступность фотографии.
4. Вносим небольшое видимое изменение фронтенда, пересобираем и повторно публикуем его файлы в существующий `static`.
5. Проверяем новую версию интерфейса, стили админки и сохранённые данные.
6. Записываем в README последовательность первого запуска и обновления; при необходимости проверяем её в отдельном Compose-проекте, не уничтожая рабочие тома.

**Файлы к концу этапа:** настройки Django, зависимости, Dockerfile бэкенда, локальный Compose, Nginx, пример окружения, осмысленные проверки и локальная инструкция.

**Этап завершён, когда:** новый человек может выполнить локальный запуск по README, а мы можем объяснить каждую служебную операцию. Работоспособность подтверждена через gateway и повторное использование данных.
