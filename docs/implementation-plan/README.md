# Kittygram: план изучения и реализации

**Маршрут: понять архитектуру → собрать проект локально → настроить доставку на сервер.**

Цель — выполнить [задание проекта](../../desc.md) и научиться объяснять, как приложение собирается, запускается, обновляется и сохраняет данные. Перед каждым изменением разбираем его назначение, после изменения проверяем результат. Этот каталог содержит план; готовность приложения отмечаем только по результатам практики.

План составлен 18 ноября 2026 года по исходникам на коммите [`7f8aa01`](https://github.com/Vital99878/kittygram-final/tree/7f8aa01ac10fd0918a7d452bd2d3ddd20abf4368). При подготовке изучены файлы и тесты; сборка, выполнение тестов и доступность сервера не проверялись.

## Как будем проходить блоки

Один блок — одна законченная тема. Если тема большая, делим её на несколько встреч. Сроки заранее не назначаем: ориентируемся на понятность и проверяемый результат.

1. Рассматриваем схему или конкретный сценарий: например, загрузку фотографии котика.
2. Разбираем новые термины и место выполнения каждой операции: компьютер, контейнер, runner или сервер.
3. Предсказываем результат изменения и возможную причину ошибки.
4. На этапе реализации вносим небольшое изменение и запускаем соответствующую проверку.
5. Объясняем результат своими словами и фиксируем рабочий шаг отдельным коммитом.

Каждую новую команду объясняем через четыре вопроса: **где выполняется, что получает, что изменяет, как проверить результат**. Для файла разбираем назначение значимых секций и связь с архитектурой. Запоминать синтаксис наизусть не требуется.

При возврате к проекту достаточно назвать номер блока. Отметка о прочтении объяснения сама по себе не означает, что практика выполнена.

## Особенности задания, которые учитываем заранее

1. **На учебной картинке пропущен `media`.** Текст задания требует три тома: `static`, `media`, `pg_data`. Все три включены в план.
2. **Выданный frontend запускает собственный HTTP-сервер.** Целевая схема использует Nginx для выдачи сборки из общего `static`. На этапе 1 выбираем поведение, на этапе 2 реализуем его, например переопределяя команду контейнера в Compose.
3. **Корневой `pytest` включает внешние приёмочные проверки.** Они требуют опубликованных образов и работающего сайта. До первой публикации выполняем локальные проверки, после деплоя — полный набор приёмочных. Иначе возникнет круговая зависимость.
4. **В текущем дереве нет отдельных backend unit tests.** Успешный запуск команды, выполнившей ноль тестов, не подтверждает работоспособность API. План включает небольшие осмысленные проверки бэкенда.
5. **В шаблоне указаны конкретные версии инструментов.** Перед сборкой сверяем совместимость Python и зависимостей, версии Node.js, Nginx, PostgreSQL и Actions. Требование курса `postgres:13` фиксируем отдельно. Обновление версий — явное решение, которое проверяем на совместимость с заданием.

Подробности о предоставленных тестах и формате `tests.yml` — в [этапе 3](03-cicd-deployment.md).

## Где заканчивается эта работа

Основной результат — один понятный проект с Docker Compose и GitHub Actions на учебном сервере. Jenkins, GitLab CI, Kubernetes, Terraform и отказоустойчивый кластер в этот маршрут не входят. HTTPS, отдельная staging-среда, расширенный мониторинг и автоматическое резервное копирование можно изучать следующим шагом; они не подменяют критерии текущего задания.

Откат и различие между томом и резервной копией разбираем уже здесь, поскольку они помогают понять цену ошибок при обновлении. Развёртывание не объявляем бесшовным: для учебной схемы допустимо краткое прерывание обслуживания, которое нужно понимать и наблюдать.
